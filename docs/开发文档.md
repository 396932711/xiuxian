# 《宗门》开发文档

> 本文档为**技术开发与版本计划**文档。游戏玩法设计见 [设计文档.md](./设计文档.md)；**版本开发计划以本文档为准**。

## 一、版本开发计划

### v1.0 · 阶段1最小可玩原型（范围调整：新增掌门系统，待开发）

**目标**：让孩子以"掌门"身份亲自下场，做出最核心的"掌门建宗门+收灵石"闭环，孩子能直观看到自身成长。

**实现功能**：

1. **资源**：仅灵石 1 种
2. **建筑（3 个）**：宗门大殿（核心）/ 灵矿场（生产）/ 招募堂（功能）
3. **掌门角色（新增）**：
   - 默认存在（新存档即创建，名"小掌门"），头像默认立绘，支持**本地上传换图**（FileReader 存 DataURL 进存档）
   - 可改名（1-6 字符）
   - 可分配至灵矿场采集 / 召回，规则同弟子
   - 有独立境界与等级（练气 1-10 级）、经验与升级，**产出 ×1.5 + 根骨 1.2**
   - **士气加成**：掌门在岗时同矿场所有弟子产出 +10%
   - **不计入弟子数量上限**（仅占用矿场工位上限）
   - UI：顶部栏固定展示掌门头像+名字+等级（点击进详情）；弟子列表置顶+金色徽章
4. **弟子**：招募、分配至灵矿场采集、练气境界 1-10 级、修炼升级、状态（空闲/采集中，召回无损）
5. **自动产出与离线**：矿场自动产灵石（含掌门与士气加成） + 离线收益 2 小时上限
6. **UI**：主界面（顶部栏 掌门+宗门+资源 / 中部建筑 / 底部导航）、掌门详情（换图+改名+分配/召回）、建筑升级弹窗、招募界面、弟子界面
7. **持久化**：localStorage 本地存档（含掌门自定义头像 DataURL，限制大小避免溢出）

**明确不含**：筑基突破、药田/丹房/藏经阁、日常任务、弟子天赋品级（掌门天赋默认优级，v1.0 先不引入一般弟子品级）、战斗/秘境、装备。

**验收标准**：孩子能在 3 分钟内完成"**以掌门身份亲自分配至矿场 → 看到灵石增长 → 招募1名弟子 → 弟子也分配 → 升级一次矿场/大殿**"的完整闭环，并能上传自己的 Q 版图片作为掌门头像。

## 二、技术选型

### v1.0 选型：单文件 HTML + 原生 JS + localStorage

**理由**：

* 无构建步骤，孩子双击 `index.html` 即可在浏览器打开

* 迭代快，适合亲子边做边试

* localStorage 满足单机存档需求，无需后端

**技术栈**：HTML / CSS / 原生 JS (ES6+)，**v1.0 不引入任何框架与依赖**。

### 后续版本迁移路径

* **v1.1**：仍可单文件，按需把 CSS/JS 拆出为独立文件

* **v1.2+**：若复杂度上升，迁移至 Vite + 原生 ES 模块化（仍不引入框架，保持孩子可读）

* **战斗/动画密集时**再评估是否引入轻量渲染库

## 四、模块设计

v1.0 单文件内按职责分区（用注释分隔，便于后续拆分）：

| 模块           | 职责                                                           |
| ------------ | ------------------------------------------------------------ |
| **Config**   | 数值常量集中管理（产出系数、升级公式参数、掌门加成）                           |
| **Save**     | 存档/读档/离线结算（含掌门自定义 DataURL 头像持久化）                                 |
| **GameLoop** | 定时 tick，驱动产出（含士气加成）与渲染                                         |
| **Resource** | 灵石增减                                                         |
| **Building** | 升级、工位、解锁依赖                                                 |
| **Leader**   | 掌门子模块：改名、换图、分配/召回、修炼（逻辑与弟子共享函数，但属性 ×1.5、士气加成生效）      |
| **Disciple** | 招募、分配、修炼、状态机                                                   |
| **Render**   | 渲染顶部栏（掌门+宗门+资源）/建筑卡片/弹窗/弟子列表（掌门置顶 + 徽章）                 |

## 五、数据模型

### 存档结构（save）

```js
{
  version: "1.0",
  lastSaveTime: 1690000000000,   // 离线结算基准时间戳
  sect: { name: "无名宗门" },
  resources: { lingshi: 0 },
  buildings: {
    dian:   { level: 1 },                    // 宗门大殿
    kuang:  { level: 1, workerIds: [] },     // 灵矿场（分配中的弟子id，包含掌门 id "d_0"）
    zhaomu: { level: 1, refreshCdEnd: 0 }    // 招募堂（刷新CD结束时间戳）
  },
  // 掌门（新存档即创建，唯一，id 固定为 "d_0"）
  leader: {
    id: "d_0",
    name: "小掌门",          // 可改名
    realm: "练气",
    level: 1,
    exp: 0,
    status: "idle",          // idle | mining（状态机同弟子）
    assignTo: null,          // null | "kuang"
    base: { root: 1.2 },     // 掌门默认"优"级根骨
    isLeader: true,
    avatarDataUrl: null      // 自定义头像；null 时使用默认立绘 leader.jpg
  },
  disciples: [
    {
      id: "d_1",
      name: "张道凡",          // 可改名；招募时由名字库随机组合生成
      realm: "练气",
      level: 1,
      exp: 0,
      status: "idle",        // idle | mining
      assignTo: null,        // null | "kuang"
      base: { root: 1.0 }   // 根骨倍率（v1.0 普通弟子默认 1.0）
    }
  ],
  nextDiscipleId: 2
}
```

> **掌门与弟子的关系**：掌门作为独立字段 `leader`，但在 `buildings.kuang.workerIds` 中用统一 id "d_0" 计入在岗列表；弟子列表渲染时把 leader 拼接到数组头部并置顶，便于 UI/产出循环复用同一套函数。掌门 id "d_0" 不参与 `nextDiscipleId`。

### 解锁与依赖规则

* 其他建筑等级上限：`otherLevelMax = dian.level`（大殿等级）
* 弟子数量上限：`discipleCap = 2 + dian.level`，**掌门不计入此上限**（弟子容量按 state.disciples.length 计算）
* 灵矿场工位上限：`kuangCap = 1 + kuang.level`，掌门上岗同样占一个工位（模拟"掌门亲自挖矿"）

### 名字库与改名（v1.0 已确认）

**结论**：弟子名字采用**内置国风名字库随机组合** + **支持玩家自定义改名**。

**名字库（Config 常量，不入存档）**：

```js
const NAME_LIB = {
  surnames: ["张","王","李","赵","陈","林","周","沈","顾","苏",
             "萧","楚","凌","叶","秦","墨","白","云","风","陆"],
  given:    ["道凡","清风","明月","云鹤","青衣","子期","长歌","无尘","若虚","观山",
             "听雨","辞树","归尘","忘机","问渠","知秋","望舒","星河","怀瑾","漱石"]
};
// 招募时随机组合：name = random(surnames) + random(given)，如"凌忘机"
```

**改名机制**：

* 弟子详情页名字旁提供"改名"按钮（或直接点击名字进入编辑）
* 弹出输入框，输入新名字（限制 **1-6 个字符**），确认后写入 `save.disciples[i].name`
* 名字字段在存档 schema 中为字符串，招募时初始值来自名字库随机组合，后续可被玩家覆盖
* 名字库作为 Config 常量，方便后续让孩子参与扩充（亲子参与设计点）

## 六、核心循环设计

### tick 机制

* `setInterval(render, 1000)`：每 1 秒刷新 UI（资源数、倒计时）

* `setInterval(produce, 10000)`：每 10 秒结算一次产出与经验

### 产出结算（每 10 秒）

```js
// 伪代码：矿场在岗弟子/掌门产出灵石（含士气加成）
const leaderMining = buildings.kuang.workerIds.includes("d_0");
const moraleMul = leaderMining ? 1.10 : 1;   // 掌门在岗：士气 +10%
for (const id of buildings.kuang.workerIds) {
  const d = id==="d_0" ? state.leader : disciples.find(x=>x.id===id);
  const leaderMul = id==="d_0" ? 1.5 : 1;     // 掌门基础产出 ×1.5
  const gain = 1.5 * (1 + 0.1*(d.level-1)) * d.base.root * leaderMul * moraleMul;
  resources.lingshi += gain;
}
```

### 修炼结算（每 10 秒）

* 掌门与全部弟子均获经验：`exp += 1`（满级 10 级后不再增长）
* 闲置/在岗皆可获经验（孩子不操作也能一起成长）

### 离线收益（进入游戏时一次性结算）

```js
const offlineSec = Math.min(Date.now() - save.lastSaveTime, 7200); // 封顶2小时
const ticks = Math.floor(offlineSec / 10);
const leaderMining = buildings.kuang.workerIds.includes("d_0");
const moraleMul = leaderMining ? 1.10 : 1;
let gain = 0;
for (const id of buildings.kuang.workerIds) {
  const d = id==="d_0" ? save.leader : save.disciples.find(x=>x.id===id);
  const leaderMul = id==="d_0" ? 1.5 : 1;
  gain += 1.5 * (1+0.1*(d.level-1)) * d.base.root * leaderMul * moraleMul * ticks;
}
resources.lingshi += gain;
// 弹窗："离线 X 分钟，收获灵石 ×gain"
```

## 七、数值公式落地（v1.0）

| 项          | 公式                                                           | 示例                                         |
| ---------- | ------------------------------------------------------------ | ------------------------------------------ |
| 弟子产出 /10s  | `1.5 × (1 + 0.1×(lv-1)) × root`                                | 1级=1.5，10级=2.85                            |
| 掌门产出 /10s  | `1.5 × (1+0.1×(lv-1)) × root(1.2) × 1.5掌门加成 × 士气1.10(在岗时)` | 1级=1.5×1.2×1.5×1.1=2.97；士气生效时弟子额外 +10%       |
| 建筑升级消耗（灵石） | `100 × 1.3^(lv-1)`                                             | 1→2=100，2→3=130，3→4=169                    |
| 升级所需经验（掌门/弟子共用）   | `100 × 1.3^(lv-1)`                                             | 1→2=100，2→3=130                              |
| 弟子数量上限     | `2 + dian.level`（掌门不计入）                                          | 大殿1级=3                                     |
| 矿场工位上限     | `1 + kuang.level`（掌门同样占工位）                                          | 矿场1级=2                                     |
| 招募单次消耗     | `50` 灵石（默认，可调）                        | —                       |
| 招募刷新CD     | `max(30 × 0.9^(zhaomu.level-1), 5)` 秒 | 1级=30s                  |

> 标注"默认/可调"的数值对应设计文档"待确认事项"，v1.0 先用默认值落地，试玩后调整。

## 八、UI 交互流程（v1.0）

### 主界面布局

* **顶部栏**（左→右）：
  1. **掌门入口**：头像 + "小掌门"名字 + 境界等级徽章（**点击进入掌门详情**）。头像旁有金色"掌门"徽章
  2. 宗门名 + 等级
  3. 灵石数（图标+数字）
* **中部**：3 个建筑卡片（大殿/矿场/招募堂），点击 → 弹出管理面板
* **底部导航**：弟子按钮 → 弹出弟子列表抽屉（掌门置顶）

### 掌门详情（顶部栏头像点击）

* 信息：头像（大）、名字、练气境 · Lv.N、经验进度条、产出/10s（带 ×1.5 掌门加成标识、在岗时显示"士气 +10%"）、状态
* 按钮：
  * **改名**（规则同弟子，1-6 字符）
  * **更换头像** → 点击弹出 `<input type="file" accept="image/*">` → FileReader 读取并压缩保存为 DataURL（超过 256KB 提示"图片过大，请更换更小的图片"）
  * **分配至矿场** / **召回**（掌门不计入弟子上限，但占矿场工位）

### 建筑管理面板

* **宗门大殿**：当前等级 / 弟子上限 / 下一级解锁说明 + 升级按钮（灵石不足置灰）

* **灵矿场**：工位占用 X/Y + 升级按钮 + "分配弟子"入口（列表含掌门，掌门单独行高亮）

* **招募堂**：招募按钮 + 单次消耗 + 刷新倒计时

### 弟子列表与详情

* 列表第 0 位**置顶**掌门（金色"掌门"徽章 + 淡金色描边背景），不可删除、不可解雇
* 其他行：头像 + 名字 + 境界等级 + 状态标签
* 点击弟子 → 详情：属性 + "改名" + "分配至矿场" / "召回" 按钮

### 招募结果反馈

* 弹出弟子卡片 + 简单 CSS 光效动画

## 九、v1.0 开发里程碑（任务拆解，已增加掌门子步骤）

按顺序实现，每步可独立验证后再进入下一步：

1. **骨架与存档** — 存档结构增加 `leader` 字段 + Save/Load + 离线结算骨架（含头像 DataURL 安全容错）
2. **掌门基础 UI** — 顶部栏掌门头像+名字+等级，点击进详情；默认立绘 `leader.jpg` 就位
3. **掌门改名与换图** — 详情页改名（1-6字符）+ 本地图片上传换图（FileReader → DataURL，超 256KB 提示）
4. **资源与主循环** — 灵石显示 + 每 10 秒产出 tick（先按掌门 1 人产出验证）
5. **宗门大殿** — 升级 + 消耗公式 + 弟子上限联动（掌门不计入）
6. **弟子与招募堂** — 招募（名字库随机命名）+ 弟子列表 + 状态字段 + 改名功能
7. **灵矿场分配** — 掌门与弟子共用分配/召回（召回无损）+ 矿场产出结算（**含掌门 ×1.5 加成 + 士气 +10%**）
8. **弟子/掌门修炼升级** — 经验积累 + 升级 + 产出系数提升（掌门与弟子共用公式）
9. **离线收益弹窗** — 进入结算 + 收获提示（含掌门加成）
10. **弟子列表置顶掌门** — 掌门置顶 + 金色徽章 + 淡金描边；掌门不在"招募弟子"列表显示（因为不从招募来）
11. **数值调优与试玩** — 验证新版验收标准：掌门亲自下场 + 招募弟子 + 升级 3 分钟闭环

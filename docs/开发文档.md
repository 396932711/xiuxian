# 《宗门》开发文档

> 本文档为**技术开发与版本计划**文档。游戏玩法设计见 [设计文档.md](./设计文档.md)；**版本开发计划以本文档为准**。

## 一、版本开发计划

### v1.0 · 阶段1最小可玩原型（✅ 已完成）

**目标**：让孩子以"掌门"身份亲自下场，做出最核心的"掌门建宗门+收灵石"闭环，孩子能直观看到自身成长。

**实现功能**：

1. **资源**：仅灵石 1 种
2. **建筑（3 个）**：宗门大殿（核心）/ 灵矿场（生产）/ 招募堂（功能）
3. **掌门角色**：
   - 默认存在（新存档即创建，名"小掌门"），头像默认立绘，支持**本地上传换图**（FileReader 存 DataURL 进存档）
   - 可改名（1-6 字符）
   - 可分配至灵矿场采集 / 召回，规则同弟子
   - 有独立境界与等级（练气 1-10 级）、经验与升级，**产出 ×1.5 + 根骨 1.2**
   - **士气加成**：掌门在岗时同矿场所有弟子产出 +10%
   - **不计入弟子数量上限**（仅占用矿场工位上限）
   - UI：顶部栏固定展示掌门头像+名字+等级（点击进详情）；弟子列表置顶+金色徽章
4. **弟子**：招募、分配至灵矿场采集、练气境界 1-10 级、修炼升级、状态（空闲/采集中，召回无损）
5. **自动产出与离线**：矿场自动产灵石（含掌门与士气加成） + 离线收益 2 小时上限
6. **UI**：主界面（顶部栏 掌门+宗门+资源 / 中部建筑 / 底部导航）、掌门详情（换图+改名+分配/召回）、建筑升级弹窗、招募界面、弟子界面
7. **持久化**：localStorage 本地存档（含掌门自定义头像 DataURL，限制大小避免溢出）

**验收标准（已通过）**：孩子能在 3 分钟内完成"**以掌门身份亲自分配至矿场 → 看到灵石增长 → 招募1名弟子 → 弟子也分配 → 升级一次矿场/大殿**"的完整闭环，并能上传自己的 Q 版图片作为掌门头像。

### v1.1 · 阶段2生产体系拓展（✅ 已完成）

**计划功能**：灵药+药田、丹药+丹房、筑基境界（仅丹药突破）、藏经阁、日常任务。

**落地实现明细（2024-09 v1.5）**：
1. **药田（yaotian）**：`workerType=farming`，工位公式 `slotCap linear(base=1,perLevel=1)`，tick 产量公式 `H.producePer10s × produce.lingyaoPerMul(默认 1)`，掌门种药无士气加成；离线按同公式累计。
2. **丹房（danfang）**：`workerType=alchemy`，工位同药田；每炼丹弟子每 tick 消耗 `recipeLingyaoCostPerBatch(默认 3)` 灵药 → 产 `recipePillPerBatch(默认 1)` 丹药；灵药不足本 tick 跳过；离线结算按总批次做批量扣产。
3. **筑基境界（练气→筑基）**：`realms.lianqi.breakthrough.nextRealm=zhuji`。练气满级（10 级）后可突破；基础成功率 `0.8`，可额外吃 `pillBoostAddMax=2` 颗（每颗 +10%）→ 最高 100%；成功后 realm=筑基、Lv.1、exp=0、产出倍率自动 × 2（`realms.zhuji.baseProduceMul=2.0`）；失败温柔惩罚：`level = maxLevel - failBackLevelOffset(默认 1)` + exp=0，不删档不脱大境界。
4. **藏经阁（cangjing）**：无工位，`expBoostPerLevel=0.05` → Lv.2 起每升 1 级全员 exp × `(1 + (Lv-1)*0.05)`，掌门与所有弟子、在岗与 idle 都生效。
5. **日常任务**：`values.quests.dailyPool(5条) + dailyCount(3)` → 每天随机 3 条；支持 collect_resource(资源)/ upgrade_building(次数)/ exp_sum(经验)/ recruit_count(招募) 四种类型；底部导航索引 3（任务按钮）从占位改为打开任务弹窗，领取后按任务 reward 字典字段映射到 state.resources 对应 key（lingshi/lingyao/danyao/contribution）并 toast 提示。

**与 v1.3 配置层约定保持一致**：全部新增常量（alchemy/breakthrough/cangjing/quests + yaotian/danfang/cangjing 建筑元数据 + 24 条 UI 文案）均在 JSON 和 config.js DEFAULTS 双份同步，并通过 validate() 类型校验；index.html 新功能的数值 100% 走 `GameConfig.values.* / buildings.* / realms.* / uiText.* / H.*` helpers，无裸字面量。

### v1.3.1 · 设置页 + 存档导入/导出/重置（✅ 已完成，v1.3 之上叠加）

> 承接"v1.3 配置外置化"的另一项横向体验补齐：**把之前只能靠 F12 控制台 `localStorage.*` 操作的"备份/迁移/清档"正式做成孩子和家长都能按的按钮**。

**目标**：孩子按一下按钮就能"下载我的宗门存档给爸爸接着玩 / 从妈妈电脑拿回我的进度 / 想重开新档时安全地重开"。

**已落地内容**：

1. **新增隐藏文件输入 `<input id="saveImport" type="file" accept=".json,application/json">`**：与掌门头像上传的 `#fileUpload` 并行存在，互不干扰。
2. **SaveIO 模块（`index.html` 中）** 7 个函数：

   - `exportSaveFile()`：`Blob + <a download>` 触发下载，文件带包壳 `{__zongmen_save__:true, meta, data:<存档对象>}`，JSON 格式化缩进 2 方便记事本打开
   - `triggerImportSave()` / `showResetConfirm()` / `doReset()`：三个按钮级对外入口
3. **设置页 `openSettings()`**：底部导航第 5 位「设置」进入，4 个区块：

   - 📦 导出卡片：显示即将生成的文件名，一键下载
   - 📥 导入卡片：调系统文件选择，导入后刷新
   - 🔄 重置卡片（浅红底 + 红边视觉警示）：跳二级确认框，强制输入 `values.saveFile.confirmResetWord`
   - 🧩 调试信息卡片：storageKey / 配置来源 / warnings 条数
4. **底部导航动态渲染**：原 HTML 硬编码 4 个按钮改为 `renderBottomNav()` 按 `ui.uiText.bottomNav` 数组位置语义生成；支持 3/4/5 个按钮任意裁剪；多余按钮自动"开放中"提示。
5. **配置化**：新增 `values.saveFile.exportNamePrefix`（默认「宗门-存档」）、`values.saveFile.confirmResetWord`（默认「重置」）；新增 `uiText.*` 共 19 个设置/导入/导出/重置相关文案字段，全量纳入 ConfigLoader 的 `DEFAULTS` 回退镜像与 `validate()` 校验。

## 二、技术选型

### v1.0 选型：单文件 HTML + 原生 JS + localStorage

**理由**：

* 无构建步骤，孩子双击 `index.html` 即可在浏览器打开

* 迭代快，适合亲子边做边试

* localStorage 满足单机存档需求，无需后端

**技术栈**：HTML / CSS / 原生 JS (ES6+)，**v1.0 不引入任何框架与依赖**。

### 后续版本迁移路径

* **v1.1**：仍可单文件，按需把 CSS/JS 拆出为独立文件

* **v1.2+**：若复杂度上升，迁移至 Vite + 原生 ES 模块化（仍不引入框架，保持孩子可读）

* **战斗/动画密集时**再评估是否引入轻量渲染库

## 四、模块设计

v1.3 按职责分区：**先 ConfigLoader 加载，再业务逻辑用 `GameConfig.*` 读**。业务层**禁止新写死常量**。

| 模块 | 文件 | 职责 |
|---|---|---|
| **ConfigLoader** | `assets/config.js` | 1) fetch 6 份 JSON，失败回退 `DEFAULTS` 内嵌镜像；2) `validate()` 字段缺/错静默回退 + 控制台 warnings；3) 注入 `ui.json.themeColors` 为 CSS 变量（`--c-qing`…）；4) 暴露公式 helpers（`H.upgradeCost / H.expNeed / H.slotCap / H.genName …`）；5) 唯一入口 `window.GameConfig` + `window.H` |
| **Save** | `index.html` | 存档/读档/离线结算（含掌门自定义 DataURL 头像持久化）；存档键名读 `GameConfig.values.storageKey` |
| **SaveIO（v1.3.1 新增）** | `index.html` | 📦 导出存档为 JSON（Blob + a.download，文件名按 `saveFile.exportNamePrefix` + 宗门/掌门 + 日期）；📥 导入 JSON（FileReader + `isValidSaveObject` 6 字段 schema 校验，兼容包壳/raw 两种格式，写回 localStorage 后 `location.reload`）；🔄 重置存档（`showResetConfirm` 二次输入确认框，确认词读 `values.saveFile.confirmResetWord`）；对外入口「宗门设置」弹窗 `openSettings()` |
| **GameLoop** | `index.html` | 定时 tick 驱动产出与渲染；tick 周期读 `GameConfig.values.tickSeconds` |
| **Resource** | `index.html` | 资源增减；初始值读 `GameConfig.resources.resources[*].initialValue` |
| **Building** | `index.html` | 升级/工位/解锁依赖；元数据从 `GameConfig.buildings.buildingMeta[*]` 读，升级公式走 `H.upgradeCost(b)`、工位上限走 `H.slotCap(bId, level)` |
| **Leader** | `index.html` | 掌门子模块：改名/换图/分配/召回/修炼；属性读 `GameConfig.values.leader.*`（root / produceMul / moraleMul / defaultName …）；逻辑与弟子共享函数，加成在公式层按 `isLeader` 乘系数 |
| **Disciple** | `index.html` | 招募/分配/修炼/状态机；名字走 `H.genName()`（从 `GameConfig.nameLib` 随机组合）；招募费用/冷却走 `GameConfig.values.recruit.*` |
| **Render（v1.3.1 更新：底部导航动态）** | `index.html` | 顶部栏 / 建筑卡片 / 弹窗 / 弟子列表（掌门置顶+徽章）；**底部导航由 `renderBottomNav()` 按 `ui.uiText.bottomNav` 数组位置语义渲染**（0弟子/1建筑/2背包/3任务/4设置）；图片路径读 `GameConfig.ui.images.*`；文案读 `GameConfig.ui.uiText.*`；主题色来自注入的 CSS 变量 |

> **跨模块铁律**：如果一个数字会影响孩子调参体验 → **先加 JSON 字段 → 再在代码里 `GameConfig.xxx.yyy` 引用**，永远别直接写数字。

## 五、数据模型

### 存档结构（save）

```js
{
  version: "1.0",
  lastSaveTime: 1690000000000,   // 离线结算基准时间戳
  sect: { name: "无名宗门" },
  resources: { lingshi: 0 },
  buildings: {
    dian:   { level: 1 },                    // 宗门大殿
    kuang:  { level: 1, workerIds: [] },     // 灵矿场（分配中的弟子id，包含掌门 id "d_0"）
    zhaomu: { level: 1, refreshCdEnd: 0 }    // 招募堂（刷新CD结束时间戳）
  },
  // 掌门（新存档即创建，唯一，id 固定为 "d_0"）
  leader: {
    id: "d_0",
    name: "小掌门",          // 可改名
    realm: "练气",
    level: 1,
    exp: 0,
    status: "idle",          // idle | mining（状态机同弟子）
    assignTo: null,          // null | "kuang"
    base: { root: 1.2 },     // 掌门默认"优"级根骨
    isLeader: true,
    avatarDataUrl: null      // 自定义头像；null 时使用默认立绘 leader.jpg
  },
  disciples: [
    {
      id: "d_1",
      name: "张道凡",          // 可改名；招募时由名字库随机组合生成
      realm: "练气",
      level: 1,
      exp: 0,
      status: "idle",        // idle | mining
      assignTo: null,        // null | "kuang"
      base: { root: 1.0 }   // 根骨倍率（v1.0 普通弟子默认 1.0）
    }
  ],
  nextDiscipleId: 2
}
```

> **掌门与弟子的关系**：掌门作为独立字段 `leader`，但在 `buildings.kuang.workerIds` 中用统一 id "d_0" 计入在岗列表；弟子列表渲染时把 leader 拼接到数组头部并置顶，便于 UI/产出循环复用同一套函数。掌门 id "d_0" 不参与 `nextDiscipleId`。

### 解锁与依赖规则

* 其他建筑等级上限：`otherLevelMax = dian.level`（大殿等级）
* 弟子数量上限：`discipleCap = 2 + dian.level`，**掌门不计入此上限**（弟子容量按 state.disciples.length 计算）
* 灵矿场工位上限：`kuangCap = 1 + kuang.level`，掌门上岗同样占一个工位（模拟"掌门亲自挖矿"）

## 六、核心循环设计

### tick 机制

* `setInterval(render, 1000)`：每 1 秒刷新 UI（资源数、倒计时）

* `setInterval(produce, 10000)`：每 10 秒结算一次产出与经验

### 产出结算（每 10 秒）

```js
// 伪代码：矿场在岗弟子/掌门产出灵石（含士气加成）
const leaderMining = buildings.kuang.workerIds.includes("d_0");
const moraleMul = leaderMining ? 1.10 : 1;   // 掌门在岗：士气 +10%
for (const id of buildings.kuang.workerIds) {
  const d = id==="d_0" ? state.leader : disciples.find(x=>x.id===id);
  const leaderMul = id==="d_0" ? 1.5 : 1;     // 掌门基础产出 ×1.5
  const gain = 1.5 * (1 + 0.1*(d.level-1)) * d.base.root * leaderMul * moraleMul;
  resources.lingshi += gain;
}
```

### 修炼结算（每 10 秒）

* 掌门与全部弟子均获经验：`exp += 1`（满级 10 级后不再增长）
* 闲置/在岗皆可获经验（孩子不操作也能一起成长）

### 离线收益（进入游戏时一次性结算）

```js
const offlineSec = Math.min(Date.now() - save.lastSaveTime, 7200); // 封顶2小时
const ticks = Math.floor(offlineSec / 10);
const leaderMining = buildings.kuang.workerIds.includes("d_0");
const moraleMul = leaderMining ? 1.10 : 1;
let gain = 0;
for (const id of buildings.kuang.workerIds) {
  const d = id==="d_0" ? save.leader : save.disciples.find(x=>x.id===id);
  const leaderMul = id==="d_0" ? 1.5 : 1;
  gain += 1.5 * (1+0.1*(d.level-1)) * d.base.root * leaderMul * moraleMul * ticks;
}
resources.lingshi += gain;
// 弹窗："离线 X 分钟，收获灵石 ×gain"
```

## 七、数值公式落地（v1.3 已配置化）

> 下列公式中出现的所有常量均来自 `assets/config/*.json`，代码不再写死。改 JSON → 保存 → 刷新 = 立即生效。公式 helpers 统一走 `assets/config.js` 暴露的 `H.*`：

| 项 | 公式（含配置字段来源） | Helper | 示例 |
|---|---|---|---|
| 弟子产出 /10s | `produce.basePer10s × (1 + produce.perLevelMul × (lv-1)) × base.root × realms[realm].baseProduceMul` | `H.producePerTick(d, buildingId)` | 1级练气 = 1.5；10级练气 = 2.85 |
| 掌门产出 /10s | 弟子公式 × `leader.produceMul` × 在岗时全员额外 × `leader.moraleMul` | 同上（`d.isLeader` 分支） | 1级练气在岗 = 1.5×1.2×1.5×1.10 = 2.97；其余弟子额外 +10% |
| 建筑升级消耗（灵石） | `upgrade.baseCost × upgrade.growthMul^(lv-1)` | `H.upgradeCost(curLevel)` | 1→2=100，2→3=130，3→4=169 |
| 升级所需经验（共用） | `exp.baseNeed × exp.growthMul^(lv-1)` | `H.expNeed(curLevel)` | 1→2=100，2→3=130 |
| 弟子数量上限 | `discipleCapFormula.base + discipleCapFormula.perDianLevel × dian.level` | `H.discipleCap(dianLevel)` | 大殿1级 = 2 + 1 = 3（掌门不计入） |
| 矿场工位上限 | `buildings.buildingMeta.kuang.slotCap.base + perLevel × kuang.level`（线性公式，通用 `H.slotCap`） | `H.slotCap("kuang", level)` | 矿场1级 = 2（掌门同样占工位） |
| 招募单次消耗 | `recruit.cost`（灵石） | 读 `GameConfig.values.recruit.cost` | 默认 50 |
| 招募刷新 CD | `max( recruit.cdBaseSeconds × recruit.cdGrowthPerLevel^(zhaomuLv-1), recruit.cdMinSeconds )` 秒 | `H.recruitCd(zhaomuLevel)` | 1级 = 30s |
| 离线收益封顶 | `offlineCapSeconds` 秒 | `GameConfig.values.offlineCapSeconds` | 7200 = 2 小时 |
| 经验获取 / tick | `idleExpPerTick`，tick 周期 `tickSeconds` 秒 | `GameConfig.values.idleExpPerTick / tickSeconds` | 每 10s +1 exp |
| 头像压缩参数 | `avatar.compress.rawFileMaxKB / dataUrlMaxKB / maxSide / qualitySteps[...]` | `H.getAvatarCompressCfg()` | 原始 8MB → 目标 256KB DataURL |
| 掌门属性默认 | `leader.root / leader.produceMul / leader.moraleMul / leader.defaultName` | `GameConfig.values.leader.*` | root 1.2 / produceMul 1.5 / moraleMul 1.1 |

> **字段来源速查**：`produce / upgrade / exp / discipleCapFormula / recruit / offlineCapSeconds / tickSeconds / idleExpPerTick / leader / avatar` → 均在 `values.json`；`buildingMeta.*.slotCap` → `buildings.json`；`realms.*.baseProduceMul` → `realms.json`。详细字段字典见《[配置文件总览.md](./配置文件总览.md)》。

### 10.2 ConfigLoader 核心职责清单

`assets/config.js` 对外暴露 `window.GameConfig`（配置数据） + `window.H`（公式 helpers），并返回 `window.GameConfigLoaded` Promise 供业务启动前 `await`。

| 职责 | 说明 | 关键实现点 |
|---|---|---|
| **1. JSON 加载** | 6 份 JSON 并行 fetch，成功覆盖对应子树；**单个失败不影响其他**（各自 try/catch） | `Promise.allSettled` 语义手写；fetch 失败（`file://` CORS 典型）自动跳过 |
| **2. 内嵌回退** | `DEFAULTS` 必须 = 6 份 JSON 的精准镜像；保证即使所有 JSON 无法访问，游戏数值仍完整可玩 | 新增/修改配置字段时必须**两处同步**（JSON + `DEFAULTS`）；数组字段完全覆盖不拼接 |
| **3. 字段校验** | `validate(data, defaults, path, warnings)` 递归：缺字段 → 补；类型错 → 用默认值；**绝不抛异常** | 所有 warnings 收集到 `GameConfig.warnings[]`，F12 可看；孩子视角无报错 |
| **4. 主题色注入** | `applyThemeColors()` → 读 `ui.themeColors.*` → `document.documentElement.style.setProperty("--c-xxx")` | 5 个 CSS 变量名与 CSS 中使用严格对应，改 JSON 无需改 CSS |
| **5. 公式 helpers** | 把所有"配置 + 等级"的计算收进 `H.*`，业务代码不再写 `×1.3^(lv-1)` 这类表达式 | `H.upgradeCost / H.expNeed / H.slotCap / H.discipleCap / H.recruitCd / H.producePerTick / H.genName` |
| **6. 名字生成** | `H.genName()` 从 `GameConfig.nameLib.surnames` / `given` 随机挑一个拼接；数组空时回退到"小道友"兜底 | 避免孩子清空整个数组导致 undefined |
| **7. 头像压缩配置** | `H.getAvatarCompressCfg()` 返回完整压缩阶梯参数，业务层循环直到满足 `dataUrlMaxKB` | 配置外置后，孩子可尝试不同质量 |

### 10.3 新增内容时的标准流程（开发者铁律）

> 加任何"可调"功能 → **先决定放哪份 JSON 加字段 → 同步 `DEFAULTS` 对应子树 → 写代码读 `GameConfig.xxx.yyy` / `H.helper(...)` → 在《配置文件总览.md》补字段说明 → 设计文档对应表加配置来源注释**。禁止先写代码再抽配置。

典型例子：

1. **加药田（阶段2）**：
   * `buildings.json`：`order` + `"yaotian"` 条目；`buildingMeta.yaotian = {id:"yaotian", name:"药田", img:"...", workerType:"planting", slotCap:{type:"linear",base:2,perLevel:1}, produces:["lingyao"]}`
   * `realms.json` 已预留"灵药 workerType 加成"（若没加就补字段）；`resources.json` 确认 `lingyao` 条目与解锁阶段
   * `config.js` 的 `DEFAULTS.buildings` 同步同样 yaotian 条目
   * 业务代码：分配/产出逻辑读 `produces` 数组，资源 ID 直接用元数据里的"lingyao"，不要写死字符串

2. **降低弟子招募门槛（调参）**：
   * 只改 `values.json` 的 `recruit.cost=10`、`recruit.cdBaseSeconds=10`；代码不用动，刷新即可

3. **中秋限时主题**：
   * 只改 `ui.json`：`themeColors.qing` 换月白、`themeColors.gold` 换深金、`images.sceneBg` 换"中秋云海背景.jpg"；刷新瞬间换皮

### 10.4 双份维护的校验清单

每次改 `assets/config/*.json` 时，需同步完成以下 3 项中的 2+N 项（N = 是否改了字段结构）：

- [ ] **JSON ↔ `DEFAULTS` 同步**（`config.js` 里的内嵌默认值）—— 字段结构变化必做
- [ ] **字段名改了 / 加了 → 《配置文件总览.md》更新对应小节**—— 字段增删必做
- [ ] **数值曲线变化会影响孩子手感 → 设计文档第六章对应条目 + 开发文档第七章表 → 示例数字刷新**—— 建议做（便于后续迭代回看）

### 10.5 v1.3.1 SaveIO 契约与异常规范（新增）

**文件格式契约**（导出的 JSON 顶级结构固定 3 键，避免与 6 份配置 JSON 混淆）：

```
{
  "__zongmen_save__": true,                      // 识别标志，导入前必查
  "meta": {
    "_exportedAt": "2026-09-02T09:15:30.000Z",   // ISO 时间戳（便于多份存档排序）
    "_storageKey": "zongmen_save_v1",            // 导出时的存档键（便于跨 key 调档）
    "_version":    "1.2",                        // state.version
    "_note":       "《宗门》存档文件…"
  },
  "data": { /* 和 localStorage 直接 getItem 的对象完全相同：sect/resources/buildings/leader/disciples/nextDiscipleId/version/lastSaveTime */ }
}
```

**导入兼容策略**：
- 格式 A（包壳）：`raw.__zongmen_save__ === true && raw.data` 合法 → 取 `raw.data`
- 格式 B（raw）：家长从 F12 复制的字符串，若 `isValidSaveObject(raw)` 通过 → 直接用
- 任一格式失败 → toast 文案，**不写回 localStorage**，确保原进度"只读安全"

**最小 schema `isValidSaveObject(o)` 6 字段**（未来加 `state.xxx` 字段时若不做强校验，可不在此枚举）：
1. `typeof o === "object" && o !== null`
2. `typeof o.sect === "object" && typeof o.sect.name === "string"`
3. `typeof o.leader === "object" && o.leader.id === "d_0"`
4. `typeof o.resources === "object"`
5. `typeof o.buildings === "object"`
6. `Array.isArray(o.disciples) && typeof o.nextDiscipleId === "number" || typeof o.nextDiscipleId === "string"`

**重置流程 2 级安全**：
- 第 1 级：按钮视觉差异化（.danger 红色 + 浅红卡面 + 文案明确写"无法恢复"）
- 第 2 级：强制输入 `values.saveFile.confirmResetWord`（默认「重置」），大小写/前后空格敏感，trim 后比对；错即 toast 取消
